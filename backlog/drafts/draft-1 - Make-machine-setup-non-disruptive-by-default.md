## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Implement the user-approved Q1–Q9 policy in docs/plans/2026-09-29-non-disruptive-setup.md across all six setup entry points. Ordinary setup must preserve ongoing BB work, connections, terminals, development servers and other work, defer potentially disruptive changes, and continue independent safe work. This includes indirect prerequisites and shared resources, not only the BB server restart. Disruptive maintenance requires explicit per-run authorization outside BB. The user requested implementation by a subagent; repository workflow still requires an implementation plan and approval before setup-code changes. No live setup, package changes, service restarts or fleet operations are authorized.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [x] #1 All six entry points default to non-disruptive operation before their earliest mutations, preserving existing platform and exact headless gates.
- [x] #2 Potentially disruptive BB, system/package, shared-runtime, agent/skill/configuration, cleanup, dotfile and networking changes are deferred; indirect callers cannot bypass deferral, and independent safe work and log finalization continue.
- [x] #3 Safety is based on complete operation effects rather than apparent inactivity; unrecognized consumers, idle sessions and work appearing after inspection cannot authorize disruptive changes.
- [x] #4 Maintenance authorization is explicit and per-invocation, cannot be persisted or restored through environment files, and preserves ownership, credential, package-policy, readiness, recovery and platform safeguards without adding automatic reboots.
- [x] #5 First-time provisioning has no automatic safety exemption; unhealthy services and failed health checks are reported without disruptive default recovery.
- [x] #6 Existing independent automatic-updater settings remain unchanged and ordinary setup does not newly enable potentially disruptive background updaters.
- [x] #7 Results distinguish verified current, applied, deferred and failed; deferrals alone succeed with maintenance-pending reporting, actual failures remain nonzero, and unqueried or deferred updates are never claimed installed or current.
- [x] #8 Inert fixtures exercise real helpers and callers across all platforms, assert forbidden commands and protected-state preservation, cover dependency propagation and repeat runs, and include available PowerShell coverage with native limitations reported.
- [x] #9 Affected existing contracts, syntax, ShellCheck and documentation checks pass or genuine environmental blockers are documented; required shared embedded helpers remain identical.
- [ ] #10 Changed setup scripts have version bumps, README and repository guidance reflect the policy, and no live setup, application/skill execution, service repair, Tailscale change, credential exposure or fleet rollout occurs during development.
