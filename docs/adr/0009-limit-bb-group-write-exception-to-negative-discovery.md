# Limit BB group-write tolerance to negative discovery

[Issue #192](https://github.com/scowalt/machine-setup-scripts/issues/192) captured an execution machine with HOME 0750, default `.bb` 0775, enrollment state and a machine daemon, but no supported main-server evidence. Rather than repair unrelated permissions or skip every execution machine, plugin refresh tolerates group write only on the account-owned real default data-directory leaf while proving that no local server work applies; an explicit selection of that same normalized default is equivalent. Custom directories, ancestors, world write, foreign ownership and actual server state retain strict refusal.

The bounded no-follow metadata snapshot covers `bb.db`, its `-wal`, `-shm` and `-journal` sidecars, `bb-app-runtime.json`, `server-moved.json` and `server-import.json`. Any filesystem form counts as evidence, inspection uncertainty fails, and changed identities, permissions or evidence invalidate the observation. Positive evidence returns to strict verification; partial state without a database is not absence. Process discovery precedes exclusion, so a main-server claim cannot be hidden by enrollment or a machine daemon.

This intentionally narrows the earlier blanket writable-state refusal only for doing nothing: `absent` grants no cached server trust, reads no server contents and makes no native requests. It proves neither group privacy nor that a server cannot start or be concealed after the snapshot; malicious same-account/root processes remain outside the existing guarantee. See the [native contract](../research/2026-10-01-bb-plugin-refresh-api.md) and [offline regressions](../../tests/test_bb_plugin_refresh.py); native recovery still requires separate authorization and evidence.
