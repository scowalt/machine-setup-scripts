# Accept existing file group write across setup verification

The owner explicitly rejected group-write file refusals after Visual Explainer installed successfully but failed setup verification on Beelink. Across Unix setup verifiers, an existing regular file's group-write bit is accepted without permission normalization or exclusive-group, NSS, process-table or ACL privacy proofs. Existing group members may modify these files; this is an owner-accepted risk, not isolation or additional filesystem/lifecycle authority.

This supersedes the preserved regular-file group-write limits in ADR 0012 and the component-specific exceptions in ADRs 0005, 0008, 0010, 0013, 0014 and 0016. It applies to metadata, package payloads, executables, service files, locks and recovery markers, including the group-write bit on direct credential files. Independent confidentiality checks remain: accepting group write alone does not authorize group/world-readable credentials. Private file creation remains private; setup does not remove existing group write merely to pass verification. Directory policy, private profile/staging/TMPDIR boundaries and native Windows ACL policy are unchanged.

Retain ownership, world-write, type/link/multiple-link, official-content, native-result and scope checks. Changes to accepted UID/GID/mode or file identity still invalidate snapshots. Keep failures from other checks nonzero through unrelated work and log finalization. Validate with inert extracted fixtures under the audited runner; repository approval is not permission for live setup, remote chmod or rollout.
