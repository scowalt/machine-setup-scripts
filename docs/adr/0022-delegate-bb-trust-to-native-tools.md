# Delegate BB trust to native tools

The owner chose functional BB integration and substantially simpler setup code over setup-added identity and security checks. The October 29 diagnosis reproduced `discovery / ambiguous-process` when BB 0.48.0's standard `--use-system-ca` / `--use-env-proxy` arguments reached setup's two-argument check; the installed launcher matched the published package and the subsequently inspected server was healthy. Extending an argument allowlist would retain the machinery the owner explicitly wants removed.

For BB server provisioning/maintenance, machine preparation and plugin refresh, trust the configured account's BB installation and native configuration. Prefer thin native-tool calls and functional availability/readiness checks. Setup-added account/package/process/peer identity proofs, ownership/mode/ACL/link gates, ancestor checks, artifact attestations, stable security snapshots, exact launch/drop-in allowlists and environment hardening are no longer required. Remove these custom gates when simplifying the implementation rather than reproducing them in another helper or expanding compatibility lists. The owner accepts the resulting loss of setup-side detection of substituted, modified or misconfigured BB installations and state.

This supersedes BB-specific trust requirements in earlier agent instructions, plans and ADRs, including the BB portions of ADRs 0011–0014, 0017 and 0018. Historical tests asserting those refusals are not preservation requirements; replace them with behavior-oriented coverage as the code changes. Older research and incident records retain their evidence and uncertainty. Other tools' security policies, shared Node/npm policy, BB's own authentication/security mechanisms and secret redaction remain unchanged.

Keep the existing management scope: desktop stays owner-managed, exact headless/server opt-ins still govern provisioning, preparation remains separate from enrollment, and plugin refresh targets local servers rather than following a remote selection. Preserve credentials, data, user configuration, native locks and unrelated services/routes. Keep stopped-update ordering, functional readiness, stopped/safe-mode deferrals, bounded execution, failure aggregation and log finalization. These are operation and data-preservation requirements, not a mandate to reconstruct custom trust proofs. Native plugin selection, pins, rollback and CLI exit semantics remain BB's responsibility.

Plugin refresh now implements this decision with local process discovery, functional health/safe-mode requests and the bundled native CLI; it no longer attests arguments, packages, filesystem permissions, snapshots or peers. Server provisioning and machine preparation are separate paths whose existing guards remain until simplified. Validate runtime changes with inert fixtures through the audited contained runner. Neither this decision nor repository implementation authorizes live setup, BB/plugin execution, service changes or remote fixes.
